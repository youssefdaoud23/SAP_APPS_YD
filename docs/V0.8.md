# Invarture App Studio V0.8

V0.8 adds three major enterprise building blocks without introducing AI/MCP functionality:

1. generic OIDC authentication with an architecture suitable for Microsoft Entra ID,
2. a persistent reusable API Designer and runtime,
3. safe declarative Server Functions.

It also strengthens server-side authorization around SAP access, shared workspace changes and production writes.

## Authentication

Supported authentication modes are selected with `AUTH_MODE`:

- `local` - local development mode. It receives the transitional Platform Admin principal.
- `basic` - HTTP Basic using `APP_STUDIO_USER` and `APP_STUDIO_PASSWORD`.
- `oidc` - Authorization Code flow with PKCE and persistent PostgreSQL sessions.

OIDC uses:

- provider discovery,
- PKCE S256,
- state and nonce validation,
- JWKS signature validation,
- issuer/audience/time claim validation,
- encrypted short-lived login transaction cookies,
- opaque random browser session cookies,
- SHA-256 session-token hashes in PostgreSQL,
- session revocation on logout,
- persistent user/group/role resolution.

No access token, ID token, SAP credential or client secret is stored in browser application state.

### Microsoft Entra ID

The implementation is generic OIDC and is designed to work with Microsoft Entra ID when the appropriate issuer, client ID, redirect URI and optional client secret are configured.

V0.8 has automated end-to-end OIDC tests against a standards-compatible mock provider. It has not yet been certified against a real Microsoft Entra tenant.

If the provider indicates group-claim overage, V0.8 records that fact. Microsoft Graph expansion of overage groups is not implemented yet.

## Authorization

Built-in roles remain:

- Platform Admin
- Developer
- Publisher
- Viewer

Important V0.8 permissions include:

- `apps.view`
- `apps.create`
- `apps.edit`
- `apps.publish`
- `apps.deploy`
- `connections.view`
- `connections.manage`
- `api.manage`
- `functions.manage`
- `users.manage`
- `audit.view`
- `production.write`

Backend APIs enforce permissions. UI visibility is not treated as a security boundary.

SAP connection access now uses a central policy:

- all SAP access requires `connections.view`,
- SAP reads require `apps.view`,
- SAP writes require `apps.edit`,
- writes against connections explicitly marked production require `production.write`.

## API Designer

The new API Designer is available from the main navigation.

API definitions are persisted in PostgreSQL and contain:

- stable ID,
- name,
- slug,
- description,
- base path,
- draft/published/disabled state,
- numeric revision,
- created/updated principals and timestamps.

Operations contain:

- HTTP method,
- route path,
- summary and description,
- runtime mode,
- configured SAP connection,
- upstream SAP path,
- headers,
- timeout,
- enabled state,
- request/response mapping placeholders.

V0.8 implements `sap-proxy` operations. Published operations are available under:

```text
/runtime/api/<api-slug>/<operation-path>
```

The runtime supports:

- GET, POST, PUT, PATCH and DELETE,
- route parameters such as `{id}`,
- incoming query-string forwarding,
- server-side SAP authentication,
- existing SAP client/language defaults,
- centralized CSRF/session handling for writes,
- bounded upstream timeouts,
- production-write authorization,
- write audit events.

API definitions use ETag/numeric revision optimistic locking. A stale edit returns HTTP 409 instead of silently overwriting a newer definition.

### API Designer limitations in V0.8

- only `sap-proxy` runtime mode is implemented,
- request/response mapping documents are stored but not yet applied to runtime data,
- OpenAPI 3.1 import/export is not implemented yet,
- the built-in test console currently focuses on GET operations.

## Server Functions

V0.8 introduces Server Functions as a deliberately constrained declarative pipeline instead of arbitrary in-process JavaScript execution.

Published functions are invoked with:

```text
POST /runtime/functions/<function-slug>
```

Function definitions support:

- name/slug/description,
- draft/published/disabled state,
- numeric revision and ETag conflict protection,
- input schema,
- timeout,
- up to 20 pipeline steps.

Supported step types are:

### `require`

Requires a value to exist at a context path.

### `set`

Creates a named variable from literals or templates.

### `sap-request`

Calls an approved configured SAP connection using the same connector, CSRF and authorization policy as the rest of the platform.

### `respond`

Builds the returned JSON-compatible value.

Templates can reference values such as:

```text
{{input.productId}}
{{vars.message}}
{{steps.products.data}}
{{principal.username}}
```

Exact templates preserve their native JSON value where possible.

Function runtime limits include:

- 1 MB input,
- 2 MB output,
- 2 MB SAP response,
- 20 steps,
- bounded execution timeout,
- safe path resolution with prototype-pollution names blocked.

Function execution writes success/failure audit events including duration.

### Why there is no arbitrary JavaScript yet

V0.8 intentionally does not execute user-provided JavaScript with `eval` or Node's in-process `vm` API. A future script-capable runtime should use a properly isolated execution boundary with explicit resource, network and secret capabilities.

## Deployment governance

The V0.7 deployment model remains active in V0.8:

- DEV/QAS/PRD environments,
- immutable application snapshots,
- checksums,
- promotion,
- production draft blocking,
- rollback,
- custom environments,
- connection aliases,
- deployment audit history.

## Validation

V0.8 has separate GitHub Actions integration suites for:

- core App Studio/SAP/PostgreSQL behavior,
- deployment governance,
- OIDC authentication/session/RBAC behavior,
- API Designer and runtime,
- Server Functions and runtime.

The API and Server Functions suites run actual Docker containers with PostgreSQL and a mock SAP endpoint. The OIDC suite runs App Studio, PostgreSQL and a mock OIDC provider and exercises the full redirect/cookie/session flow.

## Not part of V0.8

The following are intentionally still future work:

- AI application generation,
- MCP integration,
- Workflow Designer and task inbox,
- rich Launchpad Designer,
- RFC/BAPI connector,
- Microsoft Graph group-overage expansion,
- full OpenAPI tooling,
- arbitrary isolated TypeScript/JavaScript server scripting,
- full browser E2E coverage,
- broad Neptune component parity.

## Update an existing installation

```bash
git pull
sudo docker compose up -d --build
```

Verify the checked-out and running build:

```bash
git rev-parse --short=8 HEAD
curl http://127.0.0.1:8081/api/version
sudo docker compose exec -T invarture-app-studio cat /app/build-info.json
```

The short Git SHA should match in all three places.
